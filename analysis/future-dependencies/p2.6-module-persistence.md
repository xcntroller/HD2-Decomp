## Ordering and ownership constraints

Module4 runs BEFORE11/12/13 on the real stream. Context/frame resolution depends
on the already loaded scene and existing item/model resolver collections; it does
not wait for module13 payload replay. Correct the earlier graph's broad
identity-restoration→Script dependency: **world identity availability** precedes
Script; actor *state replay* follows it. Module11 immediately looks up mission
actors; module12 restores its separate runtime actors; module13 proximity also
immediately resolves module13 IDs before actor payload replay. Later top-level
objective/marker6000 resolves mission actors again. Runtime ID and mission slot
index are separate domains even where both are stored as DWORDs.

This makes wholesale reordering into “create every object, then restore every
reference” incompatible with observed dispatch. Missing identities can be a hard
prerequisite of a branch without changing the original module order. The loaded
world/process registries must already be valid on entry; frontend resume first
initializes that world through0069C340 before state replay.

No-op module persistence does not authorize removing startup registration or
activation/cleanup methods. A reset-only reader is not a round-trip of all its
runtime caches. The caller0048DE60 ignores returned values and dereferences the
registration selected by child tag without added bounds/null validation.
A guarded native decoder may reject invalid tags explicitly, but must document
that guard and stop claiming an original-compatible successful load.
