# Actor persistence and world identity

This checkpoint supersedes the provisional “relationship repair” interpretation
in the first map. Addresses are fingerprinted client VA; provenance is in
[evidence/manifest.json](evidence/manifest.json). The [dispatch catalog](evidence/actor-persistence.json)
records concrete vtables and payload readiness. These contracts recover original
interfaces; they do not claim complete Human/Car compatibility or live verification.

## Two registries, two kinds of identity

Module13 (`008100A8`) owns mission actors constructed by Scene2/actors loading.
Reuse [SceneActorRegistry](../../recovered/game/scene_actor_registry.h) and its
confirmed loading contract; don't duplicate its owner. `004759C0` uses the actual
registered type factory, binds frame EC actor word, calls `00610230` to set
actor+10, then appends or replaces the actual identity slot. First32 slots are
reserved, may be null and have generation bytes; later slots are compacted by
swap-with-last on removal, rewriting the moved actor+10. An ID is a session
registry index, not a globally stable GUID. Actor+14 is a DIFFERENT active-list
index; `00475EC0` adjusts active membership rather than creating an actor.

`00475D50(id)` rejects negative/out-of-range IDs. For null reserved slots it
searches the retired `(actor,remaining-ms)` list BACKWARDS for matching actor+10;
otherwise returns the physical slot. This is intentional access to a still-owned
retired actor, not resurrection. `00475C50(false)` queues20000ms retirement;
`00476680` stores actor+time and notifies005A7FE0. Immediate removal clears frame
EC actor word and invokes the registered class destructor. Follow existing
00476860 lifetime handling; never destroy a borrowed reference just because its
physical slot is null. `00476A50` only recomputes counters4C/50 and selected-Human
pointer54 from actual type3 Humans, state19C==2, positive healthEC, B0, availability
and selected1A4. **It is not a generic reference-fixup pass.**

Module12 (`008100E8`) has its own runtime actor vector and ID counter+70.
`004770B0(type,frame,id)` uses registered type factory, actor virtual+2C frame
initialization, frame EC association, actor+1C=1, assigns supplied id if nonnegative
or consumes/increments counter70, then appends and invokes actor+3C(true/false)
according to authority/presentation bits. Unlike module13, runtime ID need not
be the vector position. `004772F0(id)` searches runtime vector in REVERSE comparing
actor+10; absent→null, no auto-create. `00477330(actor,active)` maintains its
separate active vector by actor+14 with swap-last removal or deferred queue when
module+6C is set. Actual call sites supply module as ECX; the apparent decompiler
argument omission must not be copied into a C++ ABI.

The apparent “relationships” are proximity scheduling, not a deferred pointer table:

  actor+10 DWORD ID, speed FLOAT (raw four bytes).
- One child2000, ten existing buckets in order: timer DWORD, interval DWORD,

  Pair bytes index proximity entries, not actor IDs.
- Reader006E07C0 clears entries/pairs but retains ten buckets;1000 allocates8-byte

staggered timer interval+100*n. Those are defaults; saved timers overwrite them.
Do not regenerate pairs on load with add(), which would send notifications and
change scheduling. Actors must exist before this prelude; raw native pointers
never enter this stream. Holes in the entries vector are not explicitly encoded
by the writer, which dereferences each entry; supported saves rely on its reached
population invariants. Invalid pair bytes are not evidence of a new ID scheme.
